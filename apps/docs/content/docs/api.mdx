## Components

`Haptic` and `HapticTarget` are aliases of the same component. Both wrap one React element. A custom component must render one host target; forwarding its ref remains the custom component's responsibility.

| Prop | Type | Default |
| --- | --- | --- |
| `children` | One target React element | Required |
| `enabled` | `boolean` | `true` |
| `disabled` | `boolean` | `false` |
| `feedback` | `HapticInput` | `'selection'` |
| `triggerOptions` | `TriggerOptions` | Unspecified |
| `webHapticsOptions` | `WebHapticsOptions` | Unspecified |
| `className` | `string` | Unspecified |
| `style` | React `CSSProperties` | Wrapper uses `inline-grid` |

`triggerOptions.intensity` adjusts vibration intensity from 0 to 1. It does not change the iOS system tick. `webHapticsOptions.debug` enables desktop preview audio; `showSwitch` controls the dependency's visible feedback switch.

```tsx
<Haptic
  feedback="light"
  triggerOptions={{ intensity: 0.7 }}
  webHapticsOptions={{ debug: false, showSwitch: false }}
  style={{ display: 'grid', width: '100%' }}
>
  <button>Continue</button>
</Haptic>
```

## Imperative feedback

`canTriggerHaptic(): HapticCapability` checks current imperative availability without creating DOM or requesting feedback. `available` describes a request route, and `observed` is always false: JavaScript cannot certify tactile output. The probe accounts for page visibility and sticky activation when the browser exposes it.

`triggerHaptic(cue?: HapticInput, options?: TriggerOptions): Promise<HapticTriggerResult>` submits the request before returning its promise. The default cue is `selection`. Vibration presets, custom forms, the per-event 1000ms duration cap, and intensity modulation match `HapticTarget`. No engine, auxiliary controls, tab stops, or accessibility nodes are created.

```tsx
function SaveAction() {
  return <button onClick={() => {
    save();
    void triggerHaptic('success').then(result => {
      if (!result.delivered) console.log(result.reason);
    });
  }}>Save</button>;
}
```

The result contains `delivered`, `mechanism`, and an optional `reason`. `delivered: true` means `navigator.vibrate` accepted the request; it does not prove a physical response. A rejection, exception, unavailable environment, invalid input, or silent pattern resolves `delivered: false` with mechanism `none`. Feedback failures never reject the returned promise.

On iOS WebKit without vibration, imperative feedback resolves unavailable even inside a synchronous click handler. Transient activation alone does not make a script-created click trusted. [WebKit's trusted-event change](https://github.com/WebKit/WebKit/commit/fc1ef83eae10068fe468587d959e868041ddfe03) explicitly rejects programmatic label activation. Use `HapticTarget` for eligible physical taps; its iOS feedback is a system tick, without success/warning/error patterns. Timers and calls after an `await` do not gain an iOS delivery promise. Physical certification remains tracked in [#9](https://github.com/bloxwap/haptic/issues/9) and the remaining native API request in [#27](https://github.com/bloxwap/haptic/issues/27).

| Reason | Meaning |
| --- | --- |
| `browser-unavailable` | Server or missing browser globals |
| `document-hidden` | Page is hidden |
| `user-activation-required` | Browser requires prior interaction, or iOS has no active interaction |
| `trusted-physical-tap-required` | iOS is active, but this imperative API cannot create a trusted tap |
| `vibration-unavailable` | No imperative platform route |
| `invalid-input` | Unknown preset or invalid timing/intensity |
| `empty-pattern` | No positive vibration duration |
| `vibration-rejected` | Browser returned false |
| `vibration-error` | Feedback request failed |

## Platform helper

`isIOSWebKitWithoutVibration(navigatorLike?: Navigator): boolean` recognizes iOS WebKit identities without the Vibration API. The default argument uses the browser navigator when available. In a server environment without it, the helper returns false.

It recognizes iPadOS desktop-mode identities, but routing recognition does not establish vibration hardware. A supplied `navigator.vibrate` takes priority over the native-switch path.

## Hook

`useIOSNativeHaptics(): boolean` returns false on the server and initial render, then resolves platform routing after mount. Use it only inside a React component or hook. It does not detect whether the user can physically feel the feedback.

## Public types

```ts
import type {
  HapticTargetProps, HapticInput, HapticPattern, HapticPreset,
  TriggerOptions, Vibration, WebHapticsOptions,
  HapticCapability, HapticTriggerResult,
} from '@bloxwap/haptic';
```

- `HapticInput`: a duration number, preset string, `HapticPattern`, or `HapticPreset`.
- `HapticPattern`: alternating on/off `number[]` durations, or `Vibration[]`.
- `Vibration`: `duration: number`, `delay?: number`, `intensity?: number`.
- `HapticPreset`: `{ pattern: Vibration[] }`.
- `TriggerOptions`: `{ intensity?: number }`.
- `WebHapticsOptions`: `{ debug?: boolean; showSwitch?: boolean }`.

Feedback types come from the retained `web-haptics` dependency. All timings use milliseconds.

## Lifecycle and events

The original target element is rendered intact. Feedback runs before its React click handler, including handlers that stop propagation or prevent default. Original handlers still control bubbling and browser defaults.

Engine resources are created when first used and released on unmount or construction-option changes. Ordinary renders and feedback/intensity changes do not recreate the engine. Unmounting ends pending feedback. Feedback errors leave the original action available.

The positioning wrapper is a `span`. Target fragments containing multiple hosts are outside the single-target contract; invalid children are rejected by React's single-element check.
