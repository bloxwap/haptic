Physical-device and VoiceOver certification remains pending in [issue #9](https://github.com/bloxwap/haptic/issues/9) and is disclosed in this release. Scoped pending-certification decisions live in `*-release.json` files under [planning](https://github.com/bloxwap/haptic/tree/main/.github/planning): the [initial release decision](https://github.com/bloxwap/haptic/blob/main/.github/planning/initial-release.json) covers `0.1.0-rc.0` and `0.1.0`; the [0.2.0 decision](https://github.com/bloxwap/haptic/blob/main/.github/planning/0.2.0-release.json) covers the imperative API and feedback-entry release; the [0.3.0 decision](https://github.com/bloxwap/haptic/blob/main/.github/planning/0.3.0-release.json) covers the performance release.

Follow the [release runbook](https://github.com/bloxwap/haptic/blob/main/.github/RELEASING.md) and [physical-device procedure](https://github.com/bloxwap/haptic/blob/main/.github/DEVICE_TESTING.md). The release workflow validates a versioned source tag, unchanged verified implementation, and recorded certification or a matching pending-certification decision before publishing. Its final registry check installs actual registry bytes into fresh React 18/19 consumers and verifies metadata, tarball identity, and browser actions.

## Before publishing

Run the package, coverage, browser, packed-consumer, size, and documentation checks. Record hardware results against the same source commit. Update the package version, root lockfile, changelog, and release notes together.

Only `packages/haptic` is publishable. The root and documentation app are private. Packed consumers must work outside the workspace in ESM, CommonJS, TypeScript, React 18/19, and server rendering.

## npm setup

Only the `publish` job in `.github/workflows/publish_npm.yml` runs on GitHub-hosted `ubuntu-24.04`, a narrow exception to the Mac-mini-only runner policy because [npm trusted publishing requires GitHub-hosted runners](https://docs.npmjs.com/trusted-publishers/). Validation and security stay on the minis. Publishing uses Node 24, pinned npm 11.6.1, `contents: read` and `id-token: write`, and `--provenance`, including during token fallback. It downloads and SHA-256-verifies the exact `npm-package` tarball produced by validation; it does not repack it.

Create the GitHub `npm-release` environment and configure required reviewers in repository settings. The workflow references that environment, but YAML alone does not enable approval protection. On npmjs.com, configure the Trusted Publisher for `@bloxwap/haptic`: organization **bloxwap**, repository **haptic**, workflow filename **publish_npm.yml**, environment **npm-release**, with direct publishing allowed. Keep the workflow filename unchanged.

Keep the org-level `NPM_TOKEN` available to this repository as a transitional fallback until trusted publishing is verified. It is exposed as `NODE_AUTH_TOKEN` only to the auth check and publish steps. npm tries OIDC first and falls back to the token if no trusted publisher is configured, so releases can continue before npm setup. After verifying an OIDC publication and its provenance, delete the secret and the two fallback env entries. The auth check accepts OIDC without a token; token-only commands such as `npm whoami`, collaborator checks, `npm deprecate`, and `npm access` still require separate token authentication.

See the [CI runner prerequisites](https://github.com/bloxwap/haptic/blob/main/docs/ci-runners.md).

## Verify the release

The GitHub tag must match the library version. Publish the exact validated package with the intended dist-tag. Install that exact version from the public registry into fresh consumer projects, then repeat format/type/React/browser smoke checks and verify package metadata and tarball identity.

Confirm the deployed docs under `/haptic/`, snippets, links, and badges refer to the actual release. Do not close the release tracker on a workflow configuration, packed tarball, or manual publish alone; retain the final registry, docs, and device evidence.
